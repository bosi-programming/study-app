# ADR-027 — Distribuição npm-global do CLI e artefato JS

- Contexto: o [ADR-013](adr-013-scaffold-do-monorepo-pnpm-sem-build.md) provou o bin do CLI de dentro do repo e o [ADR-026](adr-026-instalacao-local-do-cli-symlink-do-shim-no-path.md) fechou o item "instalar" do Definition of done com um symlink do shim, mas nenhum dos dois deixa `study` instalado como comando: o symlink quebra ao mover o repo, não vale para outra máquina e some do `PATH` de um shell sem o link. O alvo é `npm install -g <pacote>`.
- Restrição do artefato: o Node 24 recusa type stripping para `.ts` sob `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), então o `bin: ./src/main.ts` do ADR-013 só funciona localmente porque o pnpm symlinka `apps/cli` para fora de `node_modules`. O runtime tem o mesmo problema: o `src` do CLI importa `@study/core`, que é privado e exporta `./src/index.ts`. Um pacote que alcance `.ts` sob `node_modules` não roda depois de instalado.
- Restrição do empacotamento: o `npm pack` não aplica override de `publishConfig.bin`/`publishConfig.exports`; o `bin` que vale é o do manifesto e ele precisa apontar para um arquivo JS com shebang. E o `npm pack` não reescreve `workspace:*` (só o `pnpm pack` reescreve), então manter `@study/core` em `dependencies` faz o `npm install -g` recusar com `EUNSUPPORTEDPROTOCOL`.
- Decisão: publicar o CLI como `study-cli` (sem escopo) no npm e instalar global com `npm install -g study-cli`, substituindo o symlink do ADR-026. O membro `apps/cli` renomeia de `@study/cli` para `study-cli` para o nome do manifesto bater com o publicado; o `private` cai e `engines.node: ">=24"` entra.
- Artefato: `apps/cli/build.mjs` usa a API do esbuild para bundlar `src/main.ts` em `dist/main.js` (`bundle: true`, `platform: 'node'`, `format: 'esm'`, `target: 'node24'`); o core entra inlinado e o `@study/core` sai de `dependencies` para `devDependencies` (`workspace:*`). O manifesto publicado fica sem `dependencies` de runtime e nenhum caminho alcançado pelo `bin` no tarball é `.ts` sob `node_modules`.
- Manifesto publish-ready: `bin.study -> ./dist/main.js` e `files: ["dist"]`; o esbuild preserva o shebang da entrada, então o alvo nasce com `#!/usr/bin/env node`. O `exports` sai — é pacote só de `bin`, ninguém importa pelo nome.
- O `prepare` constrói o `dist/`: o `pnpm install` roda o `prepare` do membro antes de linkar `node_modules/.bin/study`, então o shim local (de que as suítes do CLI dão spawn) sempre aponta para um arquivo existente; o `npm pack` também roda o `prepare`, então o tarball leva bundle novo. Sem build no runtime.
- esbuild via `allowBuilds`: o esbuild é devDependency de `apps/cli` e o pnpm 12 bloqueia scripts de build de dependência (`ERR_PNPM_IGNORED_BUILDS`); a chave que libera é `allowBuilds: { esbuild: true }` no `pnpm-workspace.yaml`, porque o `onlyBuiltDependencies` do pnpm 10 é ignorado desde o pnpm 11. O bundle gerado fica fora do lint (`**/dist/**` no `eslint.config.js`, `dist` no ignore da varredura do `S-22`).
- Consequência: a instalação documentada passa a ser registry, não caminho de máquina; o `node_modules/.bin/study` continua existindo para o uso dentro do repo, sem ser a instalação. `core` e `golden` seguem privados e consumidos direto do `src`; só o CLI ganha artefato.
- Supera o [ADR-026](adr-026-instalacao-local-do-cli-symlink-do-shim-no-path.md) integralmente e o [ADR-013](adr-013-scaffold-do-monorepo-pnpm-sem-build.md) parcialmente: o "sem build" e o `bin: ./src/main.ts` deixam de valer para o artefato publicado.
- Alternativas rejeitadas: manter o symlink local ([ADR-026](adr-026-instalacao-local-do-cli-symlink-do-shim-no-path.md)) — não deixa um comando instalado de verdade; publicar também o core — dois artefatos, coordenação de versão e dois publishes para um CLI de uso próprio; commitar uma entrada JS — o `src` continua sendo a fonte e o artefato comita divergência; só `prepack` — quebra o shim local do `pnpm install` limpo.
