# ADR-022 — Export/import do JSON v1: isenções do contexto e merge por updated_at

- Contexto: o contrato JSON v1 está fixado no `docs/especificacao/MODELO-DE-DADOS.md` desde antes de existir código que o lesse. A ENG-6 escreveu o `dumpJsonV1` para o backup do `init --reset` ([ADR-012](adr-012-init-destrutivo-com-backup-e-confirmacao-reforcada.md)) e a ENG-8 o reusou no export automático do arquivo morto ([ADR-021](adr-021-ciclo-de-vida-do-item-e-arquivo-morto.md)) — nas duas pontas ele é só um **escritor**: nem o backup do `init` nem o arquivo do dia podiam voltar para um banco. A ENG-9 (BOS-34) precisa dos dois comandos que fecham o ciclo, e ao mesmo tempo esbarra em duas regras de contexto que o [ADR-021](adr-021-ciclo-de-vida-do-item-e-arquivo-morto.md) acabou de criar: o portão de `schemaVersion() !== 1` e o gancho da migração, que o `docs/especificacao/CLI.md` descreve como "no início de todo comando". Quatro decisões não estavam tomadas: onde mora o leitor, quem fica isento das duas regras, como o conflito de UUID é resolvido e o que exatamente o import grava.
- Decisão: o **leitor mora no CLI**, em `apps/cli/src/output/json.ts`, ao lado do `dumpJsonV1`, e o **merge** em `apps/cli/src/import.ts`. O `packages/core` fica intocado: o `AGENTS.md` proíbe API de Node no core e o `CORE.md` proíbe fuso horário ali dentro, e o `Date.parse` da comparação de conflito é decisão da borda. O par round-trip no mesmo arquivo é o que torna óbvio que `toItemJson`/`toReviewLogJson` e os seus inversos têm que concordar.
- Decisão: a **escada de migrações** é uma tabela pura em `apps/cli/src/output/migrations.ts` (`CURRENT_SCHEMA_VERSION`, `MIGRATIONS`, `migrateDump`), aplicada de `fromVersion + 1` até a versão atual, sem `Store`, sem I/O e sem relógio. Hoje a v1 é a primeira versão, então a tabela é vazia, "igual ou menor" resolve para 1 e a migração é no-op — a escada existe para o próximo bump não ter que inventar lugar. Versão **futura** é recusada antes da escada, com o `CliError.unsupportedSchema` que já existe (exit 2, `schema_version N não suportado`); versão ausente, string ou float é `arquivo inválido: <path>` (exit 2), porque é arquivo fora do contrato, não versão futura.
- Decisão: **`export` fica fora do portão de schema e do gancho da migração; `import` fica fora só do gancho.** O portão é exatamente o que impediria o export de rodar quando ele é mais necessário (RNF-07, saída de emergência com o banco fora do contrato); o gancho não roda no import porque migrar o estado pré-restore não muda o resultado — a migração roda de novo no comando seguinte, já sobre os dados restaurados, e disparar um export do arquivo morto ali só produziria um arquivo que ninguém pediu. A tabela de quem é isento vive no `cli.ts` (`CONTEXT_EXCEPTIONS`) e nenhum comando decide isso por conta própria; `ContextOptions` ganha `skipSchemaGate` e `skipMigrationHook`. O portão continua valendo para o import contra um banco de destino fora da v1 (exit 2, nada escrito).
- Decisão: **banco que existe e não abre como SQLite é exit 3, `banco corrompido: <path>`, em todo comando.** O `openStore` dentro do `buildContext` passa a ser embrulhado: até aqui o erro do `node:sqlite` vazava como exit 1. A tabela de exit codes do `CLI.md` define o 3 como "estado ou ambiente: algo impede a operação", então um banco ilegível pertence ao 3 em qualquer comando, não só no export — o vazamento como exit 1 era bug, não contrato.
- Decisão: **conflito de UUID resolvido pelo `updated_at`, comparado por instante (`Date.parse`), e o arquivo vence só se for estritamente mais novo.** Empate ou local mais novo não tocam no banco: escrever o mesmo valor com carimbo novo faria a segunda importação deixar de ser idempotente. A comparação é por instante e não por string porque um arquivo editado à mão pode trazer `+00:00` no lugar de `Z`, e a ordem lexicográfica de `Z` enganaria o resultado.
- Decisão: **`ReviewLog` é evento imutável** — o modelo não tem `updated_at` para ele, então a regra é inserir só se o `id` não existe, nunca sobrescrever; um `id` repetido dentro do mesmo arquivo vira uma linha só. **`cold_archive`** reconstrói o payload `{item, review_logs}` a partir do snapshot achatado e usa o `cold_archived_at` do arquivo, com a mesma regra de "arquivo estritamente mais novo". O import é **aditivo, não espelho**: item que só existe no banco local nunca é apagado.
- Decisão: o `review_log` órfão — `item_id` que não existe nem no arquivo nem no banco — recusa o **arquivo inteiro** com exit 2 `arquivo inválido: <path>`, antes de qualquer escrita. A FK de `review_logs` está ligada e um import que descarta histórico em silêncio é pior que um que recusa.
- Decisão: o import grava só as chaves de `meta` que o destino já conhece — `cold_archive_after_days`, `locale`, `streak_current` e `streak_last_day` (valor visível ao usuário, é o RF-21) — e **não** grava `schema_version` (é o schema do destino, não o do arquivo) nem `last_cold_archive_export_at` (é escrituração da máquina que exportou). Chave de `meta` desconhecida no arquivo é ignorada.
- Decisão: no v1 o payload de `cold_archive` é exatamente `{item, review_logs}`. O dump achata esse objeto com um spread e o import o reconstrói; uma terceira chave de topo no payload faria o import não saber o que é snapshot e o que é campo do envelope, então **uma terceira chave é bump de `schema_version`**, não algo que o v1 tenha que adivinhar.
- Consequência: o ciclo fica fechado — o backup do `init --reset` (ADR-012) e o arquivo do dia (ADR-021) passam a ser reimportáveis, e `study export backup.json` é o bilhete de saída de uma máquina só. O `dumpJsonV1` não muda de forma; o que entra é o lado de leitura que faltava.
- Consequência: `study export <path>` sobre arquivo existente exige `--yes` (exit 1, `arquivo já existe; use --yes para sobrescrever`) e não encosta no destino sem ele; `import` não aceita flag de comando nenhuma e nunca pergunta. Os dois respondem com as contagens do arquivo e, no import, com `written`/`skipped` — é o `written: 0` da segunda rodada que torna a idempotência visível.
- Consequência: o merge inteiro roda numa única `store.transaction`, com toda a validação antes da primeira escrita; um arquivo fora do contrato não muda nada no banco.
- Consequência: o `SCHEMA_VERSION` local do `output/json.ts` passa a vir de `migrations.ts` para não haver dois números, e o único consumidor alcançado pela troca é o backup do `init --reset`, guardado pelo teste que já existe.
- Alternativa rejeitada: ler o dump no `packages/core` — o `AGENTS.md` proíbe API de Node no core (há um teste que varre `packages/core/src`) e o `CORE.md` proíbe fuso ali dentro; `Date.parse` e `readFileSync` são da borda.
- Alternativa rejeitada: fazer o `export` passar pelo portão de schema — é a situação do RNF-07 ao contrário: o export é justamente o que precisa continuar possível quando o banco está fora do contrato.
- Alternativa rejeitada: escrever um export automático do arquivo morto dentro do `import` — produziria um arquivo que ninguém pediu a partir de um estado pré-restore, e a migração roda de novo no comando seguinte.
- Alternativa rejeitada: resolver o conflito de UUID pelo `updated_at` em ordem lexicográfica — `2026-09-06T22:10:30+00:00` ordena antes de `2026-09-06T22:10:00Z` e um arquivo mais novo perderia o conflito.
- Alternativa rejeitada: tratar o `import` como espelho (apagar o que não está no arquivo) — seria sync entre dispositivos, que está fora do escopo do ticket, e transformaria um import de backup numa operação destrutiva.
- Gatilho de revisão: o `schema_version` subir para 2 (a escada deixa de ser vazia e o payload ganha a terceira chave que hoje é proibida), ou o sync entre dispositivos entrar em escopo — aí a regra de merge deixa de ser aditiva por desenho e volta à mesa.
